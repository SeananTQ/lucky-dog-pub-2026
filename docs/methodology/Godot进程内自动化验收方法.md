# Godot 进程内自动化验收：输入注入、状态断言与视口截图

## 方法概述

在可修改源码的 Godot 项目中，可以增加一个仅供开发使用的自动验收入口：启动实际游戏场景，由游戏进程内部的测试程序执行操作、检查结果并导出截图，随后自动退出。AI 助手负责编写和运行测试、读取日志及检查截图；开发者继续使用电脑处理其他工作。

本文来自《小狗来啦》的房间功能开发实践，具体实现环境为 Godot 4.6.3 Mono、C# / .NET 8 和 Windows。文中代码为 C# 示例；采用其他语言或引擎版本时，需要核对对应 API。示例片段用于说明接入方式，不是安装后即可测试任意游戏的通用插件。

本次成功依赖项目中新增的测试程序，以及 Godot 已有的信号、输入事件和渲染接口，无需新增桌面控制能力。这些技术本身已有用途，本次工作将它们组合成适合 AI 协作开发的验收流程。

## 实践起点：Win10 环境中的 Computer Use 验收受阻

在采用本方法之前，开发者曾在 Windows 10 22H2 环境中尝试通过 Computer Use 验收游戏。为避免影响《小狗来啦》的开发，当时另建了一个独立测试项目，并进行了多项尝试。测试结束后，该项目已被删除；本节依据开发者补充的历史经历记录。

当时的主要障碍是 Computer Use 无法取得所需的桌面截图。缺少可靠画面后，AI 助手无法准确判断点击坐标，操作频繁出错。使用游戏内部截图作为参照也没有直接解决问题：游戏图像中的坐标与 Windows 实际操作坐标存在偏差，不能简单照搬。

这暴露了桌面操作验收中的一条依赖链：截图是否可用、截图坐标能否正确映射到桌面坐标、真实鼠标是否点到目标，都会影响最终结果。本文没有保留当时的完整诊断记录，因此不进一步推断截图失败或坐标偏差的底层原因，也不把该经历推广为所有 Win10 环境都无法使用 Computer Use。

进程内验收为这一实际痛点提供了替代路径：直接访问游戏节点，向目标视口注入事件，再由引擎导出该视口的图像。用于游戏内部交互的测试可以在明确的视口坐标体系内执行，不必先恢复 Computer Use 的桌面截图能力，也不必把游戏截图坐标换算成 Windows 鼠标位置。

## 解决什么问题

通过操作系统控制鼠标和键盘来测试游戏，通常需要定位窗口、切换焦点、移动真实鼠标，再截取桌面画面。窗口句柄、权限、前台状态或自动化工具兼容性都可能影响测试，也可能打断开发者正在进行的工作。

### 相比占用真实鼠标的测试方式

这里比较的是通过系统鼠标执行点击和拖动的测试方式，不代表所有自动化测试软件都必须占用真实鼠标。

- **开发者可以继续使用鼠标。** Godot 接收合成输入事件，真实光标不需要跟着测试步骤移动。测试拖动小狗时，开发者仍可在浏览器里查询资料、点击链接和滚动页面，减少双方争用同一只鼠标的情况。
- **减少误点其他应用的机会。** 合成事件发送给指定的游戏视口，不会因为开发者临时切换到浏览器，就让这些合成点击直接落到浏览器上。窗口激活和其他外部影响仍需单独检查。
- **减少对桌面坐标的依赖。** 可以直接定位场景节点，或者使用目标视口坐标驱动输入。游戏截图与 Windows 操作坐标之间的映射不再是这些内部测试的前置条件；视口内部的缩放和坐标转换仍需要正确处理。
- **截图更聚焦游戏内容。** 引擎直接导出视口图像，不需要依赖桌面截图工具识别游戏窗口，也不会把开发者正在浏览的资料页面一并截入这张视口图。
- **操作和检查可以连续执行。** 测试程序按预定序列执行操作，并读取成员状态、位置和尺寸等数据，省去逐次人工操作、截图识别和工具往返。

### 实际干扰程度

本项目中，这种方式运行短促，对开发者使用电脑的影响较小。这不是“所有测试都能瞬间完成”或“绝不会抢焦点”的保证：窗口启动、图形渲染和资源加载仍会消耗资源；长动画、真实网络和操作系统交互仍有相应等待成本。首次接入应验证窗口激活、置顶及全局快捷键是否会干扰其他工作。

因此，本方法的优势是降低游戏内部验收对桌面控制能力的依赖，并在一定程度上减少对开发者正常使用电脑的干扰。涉及真实鼠标穿透、系统窗口遮挡等行为时，仍应保留桌面级验收。

## 各部分负责什么

- **AI 助手**：理解需求，编写验收步骤和断言，启动测试，阅读结果并检查图片。
- **项目测试程序**：选择测试环境，驱动实际场景，检查状态与几何结果，输出截图和完成标记。
- **Godot**：分发信号与输入事件，更新场景，渲染画面并提供视口图像。
- **开发者**：确认需求和体验，对操作系统层面、真实账号及未覆盖场景进行必要的实际测试。

Wick / MCP 可以辅助检查场景结构、编辑器状态和运行日志。本次的操作与截图核心来自项目测试代码；即使不使用 Wick，也可以通过命令行启动同样的测试入口。AI 的图片读取能力用于查看导出的 PNG。

## 三种驱动方式应分别使用

### 直接触发按钮信号

Godot 的 `Button` 继承自 `BaseButton`，已经具备 `pressed`、`button_down`、`button_up` 等信号。项目在场景或代码中连接信号，执行创建房间、切换页签等业务逻辑。测试程序可以复用已有连接。

```csharp
// 正常业务连接；不是专门为 AI 添加的按钮接口。
joinButton.Pressed += JoinSelectedRoom;

// 测试程序触发同一个信号。
joinButton.EmitSignal(BaseButton.SignalName.Pressed);
```

这种方式适合建立前置状态、遍历功能页面、验证按钮关联的业务流程。按钮信号来自引擎，具体业务处理方法由项目实现。官方信号说明见 [Godot BaseButton](https://docs.godotengine.org/en/4.6/classes/class_basebutton.html#signals)。

直接发信号省略了鼠标命中过程。即使控件不可见、被遮挡或处于禁用状态，也不能仅凭信号回调执行成功认定玩家能点击它。需要测试按钮的可点击性时，应另外检查可见与禁用状态，并通过实际输入事件验证命中和遮挡。

### 向视口注入输入事件

拖动、按压顺序和输入拦截等行为，需要让测试事件进入实际输入处理链。项目使用 Godot 的 `Viewport.PushInput()` 注入事件，没有通过 Windows 的 `SendInput` 或 `SetCursorPos` 操作真实鼠标。

```csharp
static void PushLeftButton(Viewport viewport, Vector2 point, bool pressed)
{
    viewport.PushInput(new InputEventMouseButton
    {
        ButtonIndex = MouseButton.Left,
        Pressed = pressed,
        Position = point,
        GlobalPosition = point,
        ButtonMask = pressed ? MouseButtonMask.Left : (MouseButtonMask)0,
    }, true);
}

static void PushDragMotion(Viewport viewport, Vector2 from, Vector2 to)
{
    viewport.PushInput(new InputEventMouseMotion
    {
        Position = to,
        GlobalPosition = to,
        Relative = to - from,
        ButtonMask = MouseButtonMask.Left,
    }, true);
}

// point 与 end 为目标视口的坐标。
PushLeftButton(viewport, point, true);
PushDragMotion(viewport, point, end);
PushLeftButton(viewport, end, false);
```

第二个参数为 `true`，表示传入位置已使用该视口坐标。事件可以进入 `_Input()`、控件 GUI 输入等处理阶段；事件被提前标记为已处理时，后续阶段可能不会执行。具体语义见 [Godot Viewport.push_input](https://docs.godotengine.org/en/4.5/classes/class_viewport.html#class-viewport-method-push-input)。

实现时还需要注意：

- 鼠标事件中的 `GlobalPosition` 不等于 Windows 桌面坐标。上述示例针对主视口；嵌套视口和变换后的画布需要明确坐标转换及目标视口。
- 按下、移动和松开要组成完整序列；拖动中的 `ButtonMask` 应保留左键状态。
- 需要检查拖动中间状态时，应在移动后、松开前等待必要帧，再断言抓取状态、位置或穿透开关。
- 事件注入不会把 Windows 的真实光标移动到合成坐标。若业务逻辑只读取 `DisplayServer.MouseGetPosition()` 或 Win32 鼠标状态，不能期望它自动看到注入的位置。
- 不应假设注入事件等同于改变所有全局轮询状态。依赖 `Input.IsMouseButtonPressed()` 等轮询接口的代码，需要针对所用 API 另行验证。
- 能从事件取得的位置和按钮状态，优先沿正常输入路径传递；必须依赖操作系统状态的部分，应明确保留实际系统测试或使用可替换的输入数据来源。

### 调用测试辅助方法

一些条件不适合依靠真实等待或反复操作来建立，可以提供开发专用的辅助方法。例如推进模拟服务时间、切换测试网络状态、读取当前拖动状态，或模拟某个外部显隐通知。

辅助方法适合安排场景和读取结果。正在验收的核心行为，尽量经过真实业务入口：验证拖动时应注入鼠标事件，再读取位置；直接给节点赋值只能证明节点可以放到指定位置。

## 截图从哪里来

测试程序等渲染完成后，读取当前视口纹理并保存 PNG：

```csharp
static async System.Threading.Tasks.Task SaveViewportAsync(
    Node context, string absoluteOutputPath)
{
    await context.ToSignal(
        RenderingServer.Singleton,
        RenderingServer.SignalName.FramePostDraw);

    var image = context.GetViewport().GetTexture().GetImage();
    var error = image.SavePng(absoluteOutputPath);
    if (error != Error.Ok)
        throw new System.IO.IOException($"Screenshot failed: {error}");
}
```

调用前应创建输出目录。本项目的对应实现位于 `InGameRoomSmoke.Capture()`，采用同样的等待绘制、读取图像和保存流程。官方接口索引为 [RenderingServer.frame_post_draw](https://docs.godotengine.org/en/4.6/classes/class_renderingserver.html#class-renderingserver-signal-frame-post-draw)。

导出的图像包含该视口渲染出的游戏内容，不包含背后的浏览器、桌面或 Windows 任务栏。透明背景会保留透明度，图片查看工具可能将透明区域显示为黑色或其他底色。其他原生窗口也不保证被当前视口截图包含。

这适合检查小狗重叠、面板位置、文字排版、缩放和显隐；真实桌面上的透明合成、置顶和外部遮挡仍需要桌面级观察。视觉验收应采用实际渲染路径，不能把仅跑逻辑的无头测试结果当成图形表现证据。

## 推荐的接入步骤

### 增加开发专用启动入口

为测试增加明确的命令行参数，在业务初始化前选择测试环境，并在实际场景准备好后启动验收程序。

本项目使用 `--rooms-page-smoke`。启动后仍加载实际主场景和系统面板，同时选择 Steam Mock 环境。测试入口、模拟设施和辅助控制需要从发布产物中排除；Demo 是否包含相应功能，应另外验证。

建议提供独立的测试实例标识，避免单实例机制把测试启动转交给开发者正在使用的游戏。实例隔离与数据隔离是两件事，两者都要处理。

### 隔离测试数据和外部服务

测试应使用独立内存状态或专用临时数据目录。真实存档、库存、奖励、统计和云端写入不应因自动测试发生改变。语言和缩放等测试设置优先使用不持久化的覆盖方式。

本项目复用了已有的启动级 Steam 模拟环境，并为房间测试设置独立实例范围。这是项目已经接入的能力，不是 Godot 的输入注入接口自动提供的数据保护。

网络延迟、请求失败和超时可由模拟服务生成。模拟时间推进可以加快测试，但不能替代真实服务的授权、回调、网络和跨设备验证。

### 等待明确状态，而不只等待固定秒数

UI 布局和异步业务不一定在方法返回时完成。应区分：

- 等节点就绪、成员数量达到目标或请求完成：优先等待条件，并设置超时。
- 等布局与可见性更新：等待必要的处理帧。
- 获取最终画面：等待渲染帧完成。
- 验证动画过程：按明确的动画事件或阶段取样，不只检查最终一帧。

本项目现有测试仍有短暂固定等待和等待两帧的步骤，适合当前原型。其他项目不应把“等待两帧”理解为通用稳定性保证。

### 同时记录状态、几何结果和图片

每条需求应对应可观察的结果。例如“自己的小狗在中间，面板跟随小狗，其他小狗不移动”，至少可以检查：

- 小狗的成员身份，而不只依赖节点数量或数组顺序。
- 本机小狗与显示器工作区中心的关系。
- 拖动前后每只小狗的位置差。
- 面板与小狗的水平、垂直关系及屏幕边缘避让。
- 宿主窗口是否意外移动或改变尺寸。
- 截图中的遮挡、文字、可见间距和视觉层级。

失败信息应包含期望值、实际值和测试步骤。流程结束时写出明确的 PASS / FAIL 标记，并返回相应退出状态。截图按用例和阶段命名，便于将图片与日志对应起来；条件允许时给每次运行单独目录，避免误读上一次成功的旧图片。

### 用源码定位并复核失败

AI 助手读取日志和图片后，可以沿着场景、输入、业务状态与渲染链定位问题。修复后重跑受影响用例，再检查相关模式退出与恢复路径。

仅修改文档或分析方法时，无需启动游戏。测试运行也不需要自动提交 Git；代码审阅、引擎资源生成与版本提交继续遵循项目原有流程。

## 本项目的实际入口

以下路径均相对于仓库根目录：

- 自动验收程序：`lucky-dog-rise/Scripts/Dev/Rooms/InGameRoomSmoke.cs`。
- 启动参数识别及主场景接入：`lucky-dog-rise/Scripts/ModeManager.cs`。
- 独立测试实例范围：`lucky-dog-rise/Scripts/Desktop/SingleInstanceGuard.cs`。
- 房间显示与拖动：`lucky-dog-rise/Scripts/Dev/Rooms/ModeManager.Rooms.cs`、`RoomDesktopPreview.cs`。
- 截图目录：`.local-build/room-lab`。

在仓库根目录下运行的 PowerShell 示例：

```powershell
# 按本机安装位置替换 Godot Mono 可执行文件路径。
$godotExe = 'C:\Tools\Godot\Godot_mono_win64.exe'
$projectDir = Join-Path (Get-Location) 'lucky-dog-rise'
$outputDir = Join-Path (Get-Location) '.local-build\room-lab'
New-Item -ItemType Directory -Path $outputDir -Force | Out-Null
$logPath = Join-Path $outputDir 'rooms-page-smoke.log'

# 先确保 C# 编译成功；离线构建需已有依赖还原结果。
dotnet build (Join-Path $projectDir 'LuckyDogRise.csproj')
if ($LASTEXITCODE -ne 0) { throw 'Build failed' }

& $godotExe --path $projectDir --log-file $logPath -- --rooms-page-smoke
```

Godot 可执行文件、启动器与终端组合可能影响命令是否等待游戏退出。不能仅凭启动命令返回成功认定测试完成，应确认本次日志中的最终标记和新截图；自动化运行器还应处理进程等待、超时及退出码。

使用 `--rooms-page-demo-smoke` 可以检查 Demo 模式是否排除了房间入口。已有房间用例涵盖翻译、成员显示、倍率、独立拖动、遮挡优先级、面板定位、任务栏吸附、退出恢复和部分异步边界。这些是具体用例的覆盖范围，不代表整个游戏已完成验收。

## 一次漏检带来的经验

房间模式最初的自动回归检查了“拖动自己时面板会移动”和“面板左右没有出屏”。运行结果满足这些条件，截图也成功导出，但面板实际一直贴着屏幕顶部。

原因是普通桌宠九宫格的上排位置依赖原有胖窗口坐标。房间模式扩大了宿主窗口，原先的窗口顶部变成了屏幕顶部。原断言没有检查面板与小狗的垂直距离，图片检查也没有发现这一关系错误。

同一轮还缺少各小狗任务栏吸附的测试。开发者手动反馈后，回归才补上：

- 默认 1x 时，8 宫面板与本地 A 区保持普通模式的垂直关系。
- 小狗向上移动时，在仍可使用 8 宫的条件下，面板按相同距离跟随。
- 靠近屏幕边缘后，面板仍能切换到合适槽位。
- 每只小狗独立吸附、沿任务栏水平移动、上拉脱离和重新吸附。
- 关闭吸附后的自由拖动，以及缩放后保持已吸附状态。

因此，“测试执行很快”“成功截图”和“存在 PASS 日志”只能证明所写步骤完成。验收质量取决于需求是否转化成了正确的检查条件，以及检查图片时是否关注了这些条件。报告应写清具体通过项，避免把部分结果扩大为“整个交互完全正常”。

## 必须保留的验证边界

**直接信号测试**可以验证连接和业务反应，但不证明鼠标真实可点击。

**视口输入测试**可以覆盖游戏内部的事件处理、命中与拖动逻辑，但不证明 Windows 已实际投递相同输入，也不证明透明区域会让真实点击落到其他程序。即使调用真实命中函数检查了空白区域，操作系统层面仍需另外验证。

合成鼠标事件限定在游戏视口内，也不意味着所有业务影响都限定在进程内。例如，“打开官网”仍可能启动浏览器，真实平台调用仍可能发送网络请求，保存操作仍可能写入文件。输入隔离与 Mock、测试数据隔离需要分别落实。

**视口截图**可以证明某个渲染时刻的游戏画面，但不包含外部桌面合成结果；单张图也无法覆盖整个动画过程。

**模拟服务测试**可以验证客户端如何处理指定响应，但不证明真实 Steam 的账号权限、网络通信或双机同步。

**本项目的成功运行**说明这套组合在当前环境和用例中可行，不等于所有操作系统、引擎版本、输入方式或游戏都无需适配。输入法组合输入、全局快捷键、真实前台切换、多显示器与 DPI、系统窗口行为等，应根据产品需求保留专项测试。

## 分享与复用建议

最小接入可以先选择一条有价值的路径：启动实际界面，执行一次操作，检查业务结果与关键几何关系，导出一张截图，再自动退出。接着逐步补充失败、取消、切换模式和恢复等路径。

这套方法特别适合“开发者可修改源码，AI 能运行命令并读取图片”的协作环境。它让游戏向自动验收程序提供稳定入口，同时让验收结果保持可观察、可复查；真实系统与真人体验验证则用于覆盖引擎内部无法证明的部分。
